# 사진으로 배우는 Splunk: 검색 한 줄부터 보안 로그 분석까지

**목표:** 검색문을 복사하는 데서 끝내지 않고, “무엇을 찾고 싶은지 → 어떤 조건을 쓰는지 → 결과가 무엇을 뜻하는지”를 스스로 설명할 수 있게 되는 것입니다.

이 문서의 사진 8장은 앞선 실습에서 로컬 Splunk에 접속해 검색한 실제 화면입니다. 사진은 당시 결과이며, 이번 개정에서는 그 화면의 의미를 더 자세히 풀었습니다. 작은 계산 표는 이해를 위한 별도 예시로 표시했습니다.

보안 로그는 학습용 프로그램이 만든 합성 기록입니다. 실제 방화벽·보안 장비를 설치하거나 실제 공격을 실행한 결과는 아닙니다. 따라서 이 문서에서 “공격”은 먼저 **공격 상황을 가정한 기록**이라는 뜻으로 읽으면 됩니다.

## 준비와 화면 읽기

### 이 자료만으로도 공부할 수 있나요?

가능합니다. 이 GitHub 공부용 묶음은 `README.md`와 `images/`로 구성됩니다. 사진과 설명을 읽는 데에는 별도 프로그램이 필요하지 않습니다.

직접 검색을 따라 하려면 앞서 구축한 **실행용 Splunk 프로젝트**가 필요합니다. 공부용 묶음에는 Docker 설정이나 시작 스크립트가 들어 있지 않습니다.

이미 실습 환경을 가진 경우:

1. Docker Desktop을 실행합니다. Docker는 이 실습의 Splunk와 로그 생성기를 실행하는 프로그램입니다.
2. `docker-compose.yml`, `start.ps1`이 들어 있는 **실행용 프로젝트 폴더**에서 PowerShell을 엽니다.
3. 다음 명령을 실행합니다.

```powershell
.\start.ps1
```

4. 브라우저에서 <http://localhost:8000>에 접속합니다. `localhost`는 “지금 사용하는 내 컴퓨터”를 뜻합니다.
5. `admin` 계정과 실행용 프로젝트의 `.env`에 설정된 비밀번호로 로그인합니다.
6. **Splunk 실습실 → Search(검색)**로 이동합니다.

### 검색은 어디에 입력하나요?

아래 사진의 상단 긴 입력란에 SPL을 붙여 넣습니다. 오른쪽 시간 범위를 **최근 24시간**으로 선택하고 초록색 돋보기 버튼을 누릅니다. 검색 완료 표시를 확인한 뒤 결과를 읽습니다.

- **이벤트 탭:** 개별 로그와 원문을 조사할 때 사용합니다.
- **통계 탭:** `stats`, `table` 등으로 만든 표를 확인할 때 사용합니다.
- **시각화 탭:** 검색 결과를 그래프 형태로 확인할 때 사용합니다.
- **대시보드:** 여러 검색 결과를 한 화면에 모아 놓은 화면입니다.

![실습실 대시보드: 전체 이벤트, 웹 오류, 로그인 실패, 보안 이벤트를 함께 확인](images/00-dashboard.png)

**사진 읽기:** “전체 이벤트”는 모든 종류의 로그 수이고, “보안 공격 이벤트”는 그중 공격 유형이 붙은 보안 이벤트 수입니다. 서로 같은 대상을 세는 숫자가 아닙니다. 예를 들어 웹 오류는 운영 장애일 수도 있으므로 곧바로 보안 공격 수에 포함되는 것은 아닙니다.

### 사진과 숫자가 달라도 정상인가요?

로그 생성기가 계속 새 데이터를 만듭니다. “최근 24시간”의 시작·종료 시각도 검색할 때마다 움직이므로 숫자는 달라질 수 있습니다.

사진들은 **2026-10-02에 촬영한 검색 결과**입니다. 지금 다시 실행한 결과라고 생각하지 마세요. 대시보드는 시간 범위를 시 단위로 맞추는 설정도 있어서 개별 검색과 총건수가 조금 다를 수 있습니다.

초기 로그인 공격·C2 시나리오는 한 번 생성한 뒤 유지됩니다. 다음 날 “최근 24시간”에서 사라졌다면 먼저 **전체 시간(All time)** 또는 생성 당시 날짜를 포함한 범위로 넓히세요. 데이터를 초기화할 필요는 없습니다.

## 로그·인덱스·소스타입·필드

### Splunk는 무엇을 하는 프로그램인가요?

서버나 애플리케이션이 남긴 기록을 모아 검색하고 집계하는 프로그램입니다. 예를 들어 “누가 로그인에 실패했지?”, “어느 기능에서 오류가 많지?”를 여러 로그 파일을 일일이 열지 않고 조사할 수 있습니다.

이 실습의 데이터 흐름은 다음과 같습니다.

```text
로그 생성기
  → 웹·인증·주문·보안 로그 파일 작성
  → Splunk가 파일의 새 내용을 읽음
  → lab 인덱스에 이벤트 저장
  → 검색창의 SPL로 조회
  → 표 또는 그래프로 결과 확인
```

### 로그와 이벤트는 어떻게 다른가요?

로그는 시스템이 남긴 기록입니다. Splunk가 검색 대상으로 다루는 기록 한 건을 **이벤트(event)**라고 부릅니다. 이 실습에서는 파일의 한 줄이 대체로 이벤트 한 건입니다. 다른 환경에서는 여러 줄로 된 오류 메시지가 이벤트 한 건일 수도 있습니다.

아래는 인증 로그 형식을 보여 주는 **설명용 예시**입니다.

```text
2026-10-02T04:00:00Z action=login user=admin src_ip=203.0.113.66 result=failure reason=bad_password app=storefront
```

이 한 줄을 말로 읽으면 “해당 시각에 `203.0.113.66`에서 `admin` 계정으로 로그인했지만 비밀번호가 맞지 않아 실패했다”입니다.

| 필드 | 예시 값 | 무엇을 알려 주나요? |
|---|---|---|
| `user` | `admin` | 로그인하려고 한 계정 |
| `src_ip` | `203.0.113.66` | 기록에 남은 접속 출발지 주소 |
| `result` | `failure` | 인증 결과: 실패 |
| `reason` | `bad_password` | 실패 사유 |
| `action` | `login` | 이 인증 로그에서 수행하려던 행위 |
| `app` | `storefront` | 대상 애플리케이션 |

**필드(field)**는 이처럼 로그에서 꺼내 이름을 붙인 정보입니다. `src_ip`가 필드 이름이고, `203.0.113.66`이 값입니다.

### index=lab은 전체 데이터베이스인가요?

`index`는 이벤트를 저장하는 논리적인 저장 공간이고, `lab`은 우리가 만든 그 공간의 이름입니다. 데이터베이스에 비유해 이해할 수 있지만 **Splunk 전체나 전체 데이터의 이름은 아닙니다.** 한 Splunk에 여러 인덱스가 있을 수 있습니다.

```spl
index=lab
```

뜻은 “선택한 시간 범위에서 `lab`에 저장된 이벤트를 찾아라”입니다. 인덱스 이름만 쓰고 시간 범위를 무시하는 검색이 아닙니다.

### sourcetype은 테이블인가요?

로그의 형식과 종류를 나타내는 분류입니다. 관계형 데이터베이스의 테이블과 일대일로 같다고 이해하면 혼동하기 쉽습니다.

```text
저장 공간: lab
  ├─ lab:web       웹 요청 형식
  ├─ lab:auth      인증 형식
  ├─ lab:orders    주문 JSON 형식
  └─ lab:security  보안 JSON 형식
```

위 그림은 같은 인덱스의 이벤트를 종류별로 분류한 것입니다. 물리적으로 하위 폴더가 생긴다는 뜻은 아닙니다.

`lab:auth`의 `:`는 이 실습에서 정한 이름의 일부입니다. `lab` 인덱스 안에 있으라는 문법이 아니며, 소스타입 이름은 다른 인덱스에서도 사용할 수 있습니다.

### 자주 보이는 이름을 먼저 익히기

| 이름 | 쉬운 뜻 | 주의할 점 |
|---|---|---|
| `source` | 로그를 읽은 파일·입력의 출처 | 이 실습에서는 로그 파일 경로 |
| `sourcetype` | 어떤 형식의 로그인가 | `source`와 다름 |
| `_raw` | 저장된 로그 원문 | 필드 값이 이상하면 원문과 비교 |
| `_time` | Splunk가 해석한 이벤트 발생 시각 | 화면 표시 시간대와 원문의 시간대가 다를 수 있음 |
| `src_ip` | 출발지 IP 주소 | 주소만으로 실제 사람의 신원을 알 수 없음 |
| `dest_ip` | 목적지 IP 주소 | 통신이 향하는 쪽 |
| `dest_port` | 목적지 서비스의 포트 번호 | 포트는 서버 안의 서비스 출입구처럼 이해 |
| `host` | Splunk 호스트 메타데이터 또는 추출된 동명 필드 | 이 실습의 보안 JSON에서는 이름 충돌이 있음 |
| `severity` | 경보에 붙인 심각도 | 이번 데이터는 생성기가 정한 값 |
| `signature` | 탐지 규칙의 이름·식별자 | 백신 서명 파일이나 사람의 서명이 아님 |

`443`은 보통 HTTPS 웹 통신에 사용하는 포트입니다. 다만 443이라고 항상 정상 웹 통신이거나 안전한 것은 아닙니다.

원문 예시의 마지막 `Z`는 UTC 시간이라는 뜻입니다. UTC 04:00은 한국 시각 13:00입니다. 원문의 시간대와 `_time`이 맞게 해석되었는지도 조사 과정에서 확인해야 합니다.

## SPL 문법과 데이터가 바뀌는 방식

SPL은 **Search Processing Language**, 즉 Splunk에서 검색하고 결과를 가공하는 언어입니다. 이 문서는 기존 SPL을 사용합니다. 화면의 “SPL2로 변환” 버튼은 누르지 않아도 됩니다.

### 첫 줄은 찾을 조건, 파이프 뒤는 처리 방법

```spl
index=lab sourcetype=lab:auth result=failure
| stats count by src_ip
| sort - count
```

말로 읽으면 다음과 같습니다.

1. `lab`에서 인증 로그 중 실패한 이벤트만 찾는다.
2. 같은 출발지 IP끼리 묶어 몇 건인지 센다.
3. 실패가 많은 IP부터 보여 준다.

첫 줄에서 공백으로 나열한 세 조건은 모두 만족해야 합니다. 즉 이 예제에서는 `AND` 관계입니다.

| 표현 | 뜻 | 읽는 방법 |
|---|---|---|
| `=` | 같은 값 | `result=failure`: 결과가 failure |
| `!=` | 다른 값 | `action!=blocked`: 값이 blocked가 아님 |
| `>=` | 크거나 같음 | `failures>=10`: 10 이상 |
| `AND` | 둘 다 만족 | A도 맞고 B도 맞음 |
| `OR` | 하나 이상 만족 | A 또는 B가 맞음 |
| `AS`, `as` | 결과 필드 이름 붙이기 | `count as failures`: 센 숫자의 이름을 failures로 |
| `by` | 묶을 기준 | `by src_ip`: 같은 IP끼리 |
| `\|` | 다음 처리 단계로 전달 | 앞 단계의 결과를 오른쪽 명령이 받음 |

`count`, `avg`, `round` 등은 기능 이름이고, `failures`, `percent` 등은 검색 작성자가 정한 결과 필드 이름입니다. 직접 이름을 바꿀 수 있지만 다음 줄에서도 같은 이름을 써야 합니다.

`src_ip="203.0.113.66"`의 따옴표는 값의 경계를 분명히 합니다. `eval`과 `where`에서 글자 값을 비교할 때는 `result="failure"`처럼 문자열에 따옴표를 붙이세요. 필드끼리 비교할 때는 `count > threshold`처럼 필드 이름을 씁니다.

### stats를 쓰면 왜 로그 원문이 없어지나요?

`stats`는 여러 이벤트를 **요약 결과 행**으로 바꿉니다. 예를 들어 이벤트 100건을 IP 3개로 묶으면 결과는 IP별 3행입니다. 이후 단계에는 집계한 필드와 `by`로 지정한 필드만 남습니다.

반면 `eventstats`는 현재 행들을 유지하면서 계산한 값을 붙이고, `table`은 현재 결과에서 표시할 필드를 선택합니다.

| 하고 싶은 일 | 명령 | 결과 모습 |
|---|---|---|
| IP별 실패 수 한 줄씩 보기 | `stats count by src_ip` | IP별 요약 행 |
| 각 이벤트 옆에 전체 건수 붙이기 | `eventstats count as event_total` | 기존 행 + 계산 필드 |
| 시간·IP·결과만 표시하기 | `table _time src_ip result` | 선택한 열로 구성된 표 |
| 바로 이전 이벤트와 시간 비교 | `streamstats` | 처리 순서를 이용한 계산값 추가 |

이 차이를 알면 “왜 `stats` 뒤에서 `user`가 안 보이지?”를 이해할 수 있습니다. 집계 과정에서 보존하지 않은 필드이기 때문입니다. 명령의 집계·필드 유지 방식은 [Splunk 공식 비교 설명](https://www.splunk.com/en_us/blog/tips-and-tricks/search-command-stats-eventstats-and-streamstats-2.html)에서도 확인할 수 있습니다.

**이 문서의 검색은 조회용입니다.** `eval`이나 `table`로 결과 모양을 바꾸는 것은 저장된 원본 로그를 수정하거나 삭제하는 작업이 아닙니다.

## 실습 1 — 로그 종류별 개수와 비율

### 무엇을 알고 싶은가?

“지금 어떤 로그가 얼마나 들어왔는가?”를 확인합니다. 인증 로그가 아예 없다면 인증 공격 검색부터 해도 결과가 나오지 않으므로, 먼저 데이터 구성을 확인하는 것입니다.

### 사진에서 실행했던 검색

```spl
index=lab
| eventstats count as total
| stats count first(total) as total by sourcetype
| eval percent=round(count/total*100, 2)
| sort - count
```

![소스타입별 이벤트 개수와 비율을 계산한 실제 검색 화면](images/01-data-overview.png)

**사진 읽는 순서:** `sourcetype`으로 종류를 보고 → `count`로 그 종류의 건수를 보고 → `total`로 분모를 확인하고 → `percent`로 전체 중 비율을 읽습니다. 네 소스타입이므로 통계 표는 네 행입니다. 상단의 이벤트 건수는 원래 검색된 이벤트 수여서 네 행과 다릅니다.

### 다섯 줄을 작은 데이터로 따라가기

다음은 계산을 쉽게 하기 위한 **가상의 10건 예시**입니다. 사진의 실제 건수와는 다릅니다.

**1단계: `index=lab`**

웹 6건, 인증 3건, 보안 1건이 검색되었다고 가정합니다. 아직은 이벤트 10개입니다.

**2단계: `eventstats count as total`**

`by`가 없으므로 검색된 전체 10건을 셉니다. 각 이벤트에 `total=10`을 붙입니다.

```text
웹 이벤트 1    total=10
웹 이벤트 2    total=10
...
인증 이벤트   total=10
보안 이벤트   total=10
```

왜 미리 전체 수를 붙일까요? 다음 단계에서 종류별로 묶어도 “전체 중 몇 퍼센트인가”의 분모를 사용할 수 있게 하려는 것입니다.

**3단계: `stats count first(total) as total by sourcetype`**

10개 이벤트를 소스타입별 3행으로 요약합니다.

| sourcetype | count | total |
|---|---:|---:|
| lab:web | 6 | 10 |
| lab:auth | 3 | 10 |
| lab:security | 1 | 10 |

여기서 `count`는 그룹 안의 건수이고, `first(total)`은 그룹에서 첫 번째로 나온 `total` 값입니다. 모두 10이므로 하나만 가져오면 됩니다.

`sum(total)`로 바꾸면 웹 그룹은 10을 6번 더해 60이 됩니다. 그래서 이 검색에서는 합계가 아니라 한 값을 가져옵니다. `first`는 “시간상 최초”를 뜻하는 함수가 아닙니다. 이 검색은 모든 total이 같아서 순서에 영향을 받지 않습니다.

**4단계: `eval percent=round(count/total*100, 2)`**

`eval`은 계산 결과를 필드에 넣습니다. 웹은 `6 ÷ 10 × 100 = 60`, 인증은 30, 보안은 10입니다. `round(..., 2)`는 소수점 둘째 자리까지 반올림합니다. 숫자 뒤에 % 기호를 자동으로 붙이는 명령은 아닙니다.

**5단계: `sort - count`**

건수가 큰 순서로 정렬합니다. `-`는 빼기가 아니라 여기서는 내림차순 표시입니다.

### 더 짧게 쓰면 왜 sum(count)가 필요한가?

같은 목적을 아래 순서로도 달성할 수 있습니다.

```spl
index=lab
| stats count by sourcetype
| eventstats sum(count) as event_total
| eval percent=round(count/event_total*100, 2)
| sort - count
```

먼저 종류별 3행을 만든 뒤 `6+3+1`을 더해 전체 10을 구합니다. 이때 `eventstats count`를 쓰면 원래 이벤트 10건이 아니라 **현재 결과 행 3개**를 세게 됩니다.

이 개선 예제는 분모를 `event_total`이라고 이름 지어 주문 로그의 금액 필드 `total`과도 구분합니다. 사진은 위의 원래 검색으로 촬영했습니다.

### 여기서 내릴 수 있는 결론

“웹 로그가 전체의 대부분이다”는 데이터 구성에 관한 결론입니다. “웹이 가장 위험하다”는 결론은 아닙니다. 적게 발생한 중요 보안 이벤트가 더 급할 수 있습니다.

## 실습 2 — 웹 오류가 많은 기능 찾기

### 먼저 용어 이해하기

웹 브라우저가 서버에 요청하면 서버는 응답과 상태 코드를 돌려줍니다.

| 상태 코드 | 이 실습에서 읽는 의미 |
|---|---|
| 200 | 요청 정상 처리 |
| 401 | 인증이 필요하거나 인증 조건을 충족하지 못함 |
| 404 | 요청한 경로의 리소스를 찾지 못함 |
| 500 | 서버 내부 오류 |
| 502 | 중간 서버가 뒤쪽 서버로부터 적절한 응답을 받지 못함 |
| 503 | 서버가 요청을 처리할 수 없는 상태 |

500~599를 묶어 **5xx**라고 부릅니다. `uri`는 요청한 경로이고, `/api/checkout`은 이 실습에서 결제 처리 경로입니다. `rt`는 생성기가 기록한 응답 시간이며 **단위는 초**입니다.

### 무엇을 알고 싶은가?

“서버 오류가 어느 기능에 몰려 있고, 오류 요청이 얼마나 오래 걸렸는가?”를 확인합니다.

```spl
index=lab sourcetype=lab:web status>=500
| stats count as errors avg(rt) as avg_response_time max(rt) as max_response_time by uri
| eval avg_response_time=round(avg_response_time, 3), max_response_time=round(max_response_time, 3)
| sort - errors
```

![웹 경로별 서버 오류 수, 오류 요청의 평균·최대 응답 시간](images/02-web-errors.png)

### 각 줄의 역할

1. 웹 로그 중 상태 코드가 500 이상인 이벤트만 남깁니다. 이 데이터의 코드 범위에서는 5xx에 해당합니다.
2. 같은 `uri`끼리 묶습니다. `count`는 오류 요청 수, `avg(rt)`는 평균, `max(rt)`는 가장 긴 응답 시간입니다.
3. 두 시간 값을 소수점 셋째 자리까지 반올림합니다.
4. 오류 요청 수가 많은 경로부터 표시합니다.

사진의 `/api/checkout` 행을 읽으면 “해당 시간 범위에서 결제 경로의 서버 오류 요청이 가장 많았다”입니다. 평균 응답 시간 3.3 정도는 약 3.3초입니다.

**평균은 전체 요청의 평균이 아닙니다.** 첫 줄에서 성공 요청을 이미 제외했으므로 **오류 요청만의 평균**입니다.

### 오류가 많으면 가장 문제가 심한 기능인가요?

요청이 많이 들어오는 기능은 오류 절대 건수도 많을 수 있습니다. 비교하려면 분모인 전체 요청 수도 보아야 합니다.

아래는 **추가 연습용 검색**입니다. 위 사진의 검색과 다릅니다.

```spl
index=lab sourcetype=lab:web
| stats count as requests count(eval(status>=500 AND status<600)) as errors by uri
| eval error_percent=round(errors/requests*100, 2)
| sort - error_percent
```

`count(eval(...))`는 괄호 속 조건이 참인 이벤트 수를 셉니다. 첫 줄에서 오류만 거르지 않은 이유는 전체 요청 수가 필요하기 때문입니다.

설명용 예로 A 기능은 10,000건 중 100건 실패하면 1%, B 기능은 100건 중 20건 실패하면 20%입니다. 오류 개수는 A가 많지만 실패 비율은 B가 높습니다.

**5xx만으로 공격을 확정할 수 없습니다.** 프로그램 오류나 서버 과부하도 같은 결과를 냅니다. 같은 시각의 공격 경보, 요청 원문, 애플리케이션 오류 로그를 더 보아야 원인을 좁힐 수 있습니다.

## 실습 3 — 반복 로그인 실패 조사

### 무엇을 알고 싶은가?

“어느 IP가 어떤 계정으로 반복해서 로그인에 실패했는가?”를 찾습니다. 비밀번호 후보를 반복해서 시도하는 공격을 **무차별 로그인 시도(brute force)**라고 부릅니다.

```spl
index=lab sourcetype=lab:auth result=failure
| stats count as failures values(user) as targeted_users min(_time) as first_seen max(_time) as last_seen by src_ip
| where failures>=10
| convert ctime(first_seen) ctime(last_seen)
| sort - failures
```

![출발지별 로그인 실패 건수와 대상 계정, 최초·마지막 실패 시각](images/03-brute-force.png)

### 각 줄의 역할

| 줄 | 무엇을 하는가 | 왜 필요한가 |
|---|---|---|
| 인증 로그 + 실패 조건 | 실패한 인증만 선택 | 성공 로그를 실패 횟수에 섞지 않기 위해 |
| `stats ... by src_ip` | 출발지별로 실패 수와 계정 목록, 처음·끝 시각 집계 | 반복 행위를 IP 단위로 보기 위해 |
| `where failures>=10` | 집계된 실패 수가 10 이상인 IP만 선택 | 소수의 오입력은 일단 줄이기 위해 |
| `convert ctime(...)` | 집계한 숫자 시각을 읽기 쉬운 날짜로 변환 | 표에서 시간을 바로 읽기 위해 |
| `sort - failures` | 실패 수 내림차순 | 많이 발생한 대상을 먼저 보기 위해 |

`values(user)`는 중복을 제거한 계정 목록입니다. `admin`으로 48회 실패했다면 목록에는 admin이 한 번만 나옵니다. 발생 순서나 각 계정의 실패 건수를 알려 주는 목록은 아닙니다.

`min(_time)`과 `max(_time)`은 각각 가장 이른 시각과 가장 늦은 시각입니다. 계산할 때 시간은 초 단위 숫자로 다뤄집니다. 이것을 Unix 시간이라고 합니다.

`failures`는 `stats`가 만든 필드입니다. 첫 줄에서 이 필드로 필터링할 수 없는 이유는 아직 계산하지 않았기 때문입니다.

### 사진에서 무엇을 확인했나?

`203.0.113.66`은 admin 한 계정에 48회 실패했습니다. 이 사례는 생성기에 넣은 공격 시나리오와 일치합니다. 다른 행에는 긴 시간에 걸쳐 여러 계정의 실패가 모여 있습니다.

하지만 실무에서 **실패 10회 = 공격 확정**은 아닙니다. 오래 집계하면 정상 오입력도 누적되고, 회사 공유기나 프록시 뒤의 여러 사용자가 하나의 IP로 보일 수 있습니다. 이때 정상 행위를 공격으로 잡는 것을 **오탐**이라고 합니다.

### 단순 건수 기준을 개선하기

아래 추가 검색은 “출발지·계정별로 5분 동안 실패가 10회 이상”인 구간을 찾습니다.

```spl
index=lab sourcetype=lab:auth result=failure
| bin _time span=5m
| stats count as failures by _time src_ip user
| where failures>=10
| sort - failures
```

`bin`은 시간을 5분 구간으로 묶습니다. `by _time src_ip user`이므로 같은 시간 구간·같은 IP·같은 계정 조합끼리 셉니다. 숫자 10은 이 실습의 연습 기준이며 모든 회사에 적용되는 정답이 아닙니다.

### 실패 뒤 성공했는지도 확인하기

```spl
index=lab sourcetype=lab:auth src_ip="203.0.113.66"
| sort 0 _time
| table _time src_ip user result reason
```

첫 줄에서 `result=failure`를 뺀 이유는 성공 기록도 보기 위해서입니다. 과거 → 현재 순서로 보면 실패가 반복되다가 성공으로 바뀌었는지 조사할 수 있습니다. 초기 시나리오에는 48회 실패 후 성공 한 건이 들어 있습니다.

`sort 0 _time`의 0은 시간 0을 뜻하지 않습니다. 정렬 시 반환 건수 제한을 없앱니다. 일반 `sort`는 별도 개수를 지정하지 않으면 기본적으로 최대 10,000개 결과를 반환하므로, 작은 실습에서는 차이가 없어도 전체 순서를 조사할 때는 구분해야 합니다. [Splunk sort 문서](https://help.splunk.com/en/splunk-cloud-platform/spl-search-reference/10.4.2604/search-commands/sort)

연속 실패 뒤 성공했다면 계정 사용자를 확인할 이유가 됩니다. 로그만으로 비밀번호가 탈취되었다고 단정할 수는 없습니다.

## 실습 4 — 보안 로그와 공격 종류 이해

### 보안 로그는 누가 만드는가?

실제 환경에서는 다음과 같은 장비·프로그램이 보안 로그를 남깁니다.

| 이름 | 쉬운 설명 | 주로 보는 것 |
|---|---|---|
| 방화벽 | 통신 허용·차단 규칙을 적용 | 출발지·목적지·포트 |
| IDS | 의심스러운 통신을 탐지하는 시스템 | 공격 패턴과 경보 |
| WAF | 웹 요청을 검사하는 웹 방화벽 | 웹 입력을 악용하는 시도 |
| EDR | PC·서버 안의 행위를 관찰하고 대응하는 도구 | 프로세스·파일·권한 관련 행위 |

이 실습에서는 이러한 로그를 흉내 낸 JSON을 생성기가 작성합니다. **JSON**은 `"이름": "값"` 형태로 정보를 표현하는 형식입니다.

설명용 보안 이벤트 예시:

```json
{
  "event_type": "web_attack",
  "attack_type": "sql_injection",
  "severity": "high",
  "action": "blocked",
  "src_ip": "198.51.100.77",
  "dest_ip": "10.20.1.20",
  "dest_port": 443,
  "signature": "WAF_SQLI_UNION_SELECT"
}
```

“해당 출발지에서 웹 서버로 향한 요청에 SQL 인젝션 탐지 규칙이 걸렸고, 심각도는 high, 조치는 blocked로 기록됐다”라고 읽습니다.

`event_type`은 큰 사건 분류, `attack_type`은 구체적인 공격 유형, `signature`는 탐지 규칙 이름입니다. 한 필드의 다른 이름들이 아닙니다.

### 공격 이름부터 이해하기

| attack_type | 쉬운 뜻 | 이 실습에서 관찰할 기록 |
|---|---|---|
| `none` | 공격 유형이 붙지 않은 배경 이벤트 | 정상 통신을 가정한 기록 |
| `port_scan` | 어떤 서비스가 열렸는지 여러 포트를 조사 | 짧은 시간에 여러 포트·IP 접촉 |
| `brute_force` | 비밀번호 후보를 반복해서 시도 | 반복 인증 공격 경보 |
| `sql_injection` | 웹 입력을 이용해 DB 질의 동작을 바꾸려는 시도 | SQL 인젝션 규칙 경보 |
| `path_traversal` | 허용된 경로 밖 파일에 접근하려는 시도 | 경로 탐색 규칙 경보 |
| `xss` | 웹페이지를 통해 사용자 브라우저에서 스크립트가 실행되게 하려는 시도 | XSS 규칙 경보 |
| `malware_callback` | 악성코드가 외부 서버에 연락하는 상황 | 반복 외부 통신 기록 |
| `privilege_escalation` | 일반 권한에서 더 높은 권한을 얻으려는 행위 | 의심스러운 권한 상승 경보 |

### 무엇을 알고 싶은가?

“어떤 유형의 경보가 얼마나 있고, 심각도와 조치는 무엇인가?”를 요약합니다.

```spl
index=lab sourcetype=lab:security attack_type!=none
| stats count values(severity) as severity values(action) as action by attack_type
| sort - count
```

![공격 유형별 건수와 심각도, 대응 조치](images/04-attack-types.png)

첫 줄은 보안 이벤트 중 `attack_type` 값이 none이 아닌 것만 선택합니다. 두 번째 줄은 공격 유형별로 경보 수와 서로 다른 심각도·조치 값을 모읍니다. 마지막 줄은 건수순으로 정렬합니다.

**Splunk가 이 검색을 통해 공격 유형을 처음 판별한 것이 아닙니다.** 생성기가 미리 기록한 `attack_type`을 검색한 것입니다. 실제 장비의 경보를 모아 분석하는 방식과 비슷한 연습입니다.

### severity와 action을 왜 같이 보나?

`severity`는 기록된 경보 심각도이고, `action`은 이 보안 로그에서 기록된 조치입니다.

| 값 | 이번 실습에서의 의미 | 이 값만으로 알 수 없는 것 |
|---|---|---|
| `medium` | 중간 심각도 | 실제 피해 크기 |
| `high` | 높은 심각도 | 공격 성공 여부 |
| `critical` | 매우 중요한 경보 | 실제 감염·침해 확정 |
| `blocked` | 해당 행위를 차단했다고 기록 | 모든 관련 공격까지 막았는지 |
| `allowed` | 통신을 허용했다고 기록 | 연결 완료·공격 성공 여부 |
| `detected` | 의심 행위를 탐지했다고 기록 | 차단했는지, 권한 상승에 성공했는지 |

사진에는 C2 콜백 20건이 critical/allowed, 권한 상승 8건이 critical/detected로 보입니다. 이 실습에서는 두 유형을 먼저 조사할 이유가 있습니다. 건수가 더 많은 포트 스캔만 보고 우선순위를 정하면 이들을 놓칠 수 있습니다.

우선순위는 심각도와 조치 외에도 대상 서버의 중요도, 탐지 정확도 등을 함께 고려합니다. 위 값은 이 학습 데이터의 분류이며 모든 제품에서 동일한 의미와 기준을 쓰는 것은 아닙니다.

인증 로그의 `action=login`과 보안 로그의 `action=blocked`는 같은 이름의 필드지만 뜻이 다릅니다. 그래서 `sourcetype`으로 어떤 로그인지 먼저 구분합니다.

### !=none과 필드가 아예 없는 것은 다른가요?

네. `attack_type!=none`은 **attack_type 값이 존재하고 none이 아닌 이벤트**를 찾습니다. 필드 자체가 없는 이벤트를 포함하는 조건이 아닙니다. 모든 보안 이벤트에 해당 필드가 있는 이 실습에서는 공격 분류를 걸러내는 용도로 사용할 수 있습니다. [Splunk의 !=와 NOT 차이](https://help.splunk.com/en/splunk-enterprise/search/search-manual/9.1/expressions-and-predicates/difference-between-and-not)

## 실습 5 — 여러 포트를 훑는 행동 찾기

### 무엇을 알고 싶은가?

이번에는 공격 이름을 바로 찾기보다 **짧은 시간에 여러 서비스에 접근한 행동 자체**를 찾습니다. 그래서 첫 줄에 `attack_type=port_scan`을 넣지 않습니다.

```spl
index=lab sourcetype=lab:security event_type=network_connection
| bin _time span=5m
| stats dc(dest_port) as unique_ports dc(dest_ip) as unique_destinations count by _time src_ip
| where unique_ports>=5 OR unique_destinations>=3
| sort - count
```

![5분 구간별 출발지 IP의 서로 다른 포트·목적지 수](images/05-port-scan.png)

### 왜 5분씩 묶나요?

하루 동안 여러 서버에 접속하는 것은 흔하지만, 짧은 시간에 여러 서비스에 접속하면 조사할 이유가 커질 수 있습니다.

`bin _time span=5m`은 다음처럼 **고정된 시간 구간**으로 묶습니다.

| 원래 시각 — 설명용 예시 | 집계에 사용하는 시각 |
|---|---|
| 10:01:20 | 10:00:00 |
| 10:04:59 | 10:00:00 |
| 10:05:00 | 10:05:00 |

항상 “각 이벤트 직전의 5분”을 계산하는 이동 구간은 아닙니다. 10:04와 10:06은 2분 차이지만 다른 구간으로 나뉩니다. 사진에서도 같은 공격 IP가 두 시간 구간에 걸쳐 보입니다.

### count와 dc는 무엇이 다른가요?

`dc`는 **distinct count**, 서로 다른 값의 수입니다.

설명용 예시로 포트가 `443, 443, 80, 22, 22`인 이벤트 5개가 있다면:

- `count`: 이벤트가 5개이므로 **5**
- `dc(dest_port)`: 포트 종류는 443·80·22이므로 **3**
- `values(dest_port)`: 서로 다른 포트 값의 **목록**

같은 포트에 반복 접속한 횟수와 여러 포트를 훑은 정도를 구분하려고 `dc`를 씁니다.

### by에 두 필드가 있으면 어떻게 묶이나요?

`by _time src_ip`는 같은 5분 구간과 같은 출발지 IP의 조합끼리 집계합니다. IP가 같아도 구간이 다르면 다른 행이고, 구간이 같아도 IP가 다르면 다른 행입니다.

그 안에서 서로 다른 목적지 포트 수, 목적지 IP 수, 이벤트 수를 각각 계산합니다.

### 사진을 어떻게 읽나요?

`203.0.113.45` 행에는 포트 8종류와 목적지 4개가 나타납니다. 숫자 8은 “목적지마다 8개씩 접속했다”는 뜻이 아니라 **그 행에 속한 전체 이벤트에서 서로 다른 포트가 8개**였다는 뜻입니다.

이 패턴은 생성기에 넣은 스캔 시나리오와 일치합니다. 다른 정상 배경 IP도 검색에 나오는 이유는 `OR` 조건 때문입니다. 포트가 2종류뿐이어도 목적지 3개 이상이면 통과합니다.

### OR를 AND로 바꾸면 무엇이 달라지나요?

집계 뒤의 조건을 다음처럼 바꿔 보는 추가 연습입니다.

```spl
| where unique_ports>=5 AND unique_destinations>=3 AND count>=10
```

세 조건을 모두 만족해야 하므로 더 적은 결과가 남습니다. 대신 **서버 하나의 여러 포트만 훑는 스캔**은 목적지 개수 조건 때문에 놓칠 수 있습니다.

정상 행위를 잘못 잡는 것이 오탐, 실제 공격을 놓치는 것이 미탐입니다. 조건을 강하게 하면 항상 좋은 것이 아니라 둘 사이의 균형이 바뀝니다. 운영 환경의 정상 접속 패턴을 보고 기준을 정해야 합니다.

## 실습 6 — 차단이 확인되지 않은 중요 경보

### 무엇을 알고 싶은가?

“중요한 경보 중 차단됐다는 기록이 없는 것은 무엇인가?”를 찾아 상세 조사 대상을 정합니다.

### 사진에서 실행했던 검색

```spl
index=lab sourcetype=lab:security severity=critical action!=blocked
| eval endpoint=mvindex(host, -1)
| table _time event_type attack_type src_ip dest_ip dest_port endpoint user signature action
| sort - _time
```

![중요 보안 이벤트의 시각, 통신 주소, 엔드포인트, 계정, 조치](images/06-critical-unblocked.png)

첫 줄은 critical이면서 action이 blocked가 아닌 이벤트를 고릅니다. `table`은 조사할 필드만 선택하고, 마지막 줄은 최근 기록부터 보여 줍니다.

이 데이터에는 action이 모두 있지만, 다른 로그에서 필드가 없으면 `action!=blocked`만으로는 “조치 미상” 이벤트까지 포함하지 않습니다.

### endpoint와 mvindex는 왜 나오나요?

**엔드포인트(endpoint)**는 여기서 조사 대상 PC나 서버를 뜻합니다.

이 실습의 보안 JSON에는 `host`가 있고 Splunk도 자체적으로 `host` 메타데이터를 붙입니다. 앞선 조회에서는 한 이벤트의 host에 `splunk-lab`과 `workstation-31`처럼 두 값이 함께 보였습니다. 여러 값을 가진 필드를 **다중값 필드**라고 합니다.

`mvindex(host, -1)`은 다중값의 마지막 값을 선택합니다. 사진을 촬영한 결과에서는 그 값이 대상 서버명이어서 `endpoint`라는 새 열에 표시했습니다.

다만 **항상 마지막 값이 실제 서버명이라는 규칙은 없습니다.** 사진 설명에 쓰인 방법과 일반적으로 재사용할 방법을 구분해야 합니다.

### 직접 따라 할 때의 권장 검색

원문 JSON의 host를 지정해서 읽으면 값 순서에 의존하지 않습니다.

```spl
index=lab sourcetype=lab:security severity=critical action!=blocked
| spath input=_raw path=host output=endpoint
| sort 0 - _time
| table _time event_type attack_type src_ip dest_ip dest_port endpoint user signature action
```

`spath`는 JSON 같은 구조화된 데이터에서 값을 꺼내는 명령입니다. `input=_raw`는 원문에서, `path=host`는 host 항목을, `output=endpoint`는 endpoint라는 이름으로 가져오라는 뜻입니다. 이것은 사진 이후 설명에서 제시하는 개선 검색입니다. [Splunk spath 문서](https://help.splunk.com/en/splunk-enterprise/spl-search-reference/9.4/search-commands/spath)

### 사진의 두 종류를 읽기

**C2 콜백:** `10.20.2.31 → 198.51.100.200:443`

출발지는 내부 PC, 목적지는 외부 주소로 설정한 합성 기록입니다. `allowed`이므로 허용 조치가 기록되었습니다. 사진의 `workstation-31`은 조사 대상 PC 이름입니다. 같은 대상과 반복 통신하는지는 다음 실습에서 확인합니다.

**권한 상승:** `svc-web` 계정, `app-server-02`

`svc-web`은 이 실습에서 웹 서비스 계정을 가정한 이름입니다. `EDR_SUSPICIOUS_SUDO`는 높은 권한으로 명령을 실행하는 sudo 사용을 의심하도록 붙인 합성 규칙 이름입니다.

확인한 사실은 **경보와 detected 조치가 기록되었다는 것**입니다. 관리자 권한을 실제로 얻었는지는 이 이벤트만으로 알 수 없습니다. 실제 조사라면 실행 명령, 계정 권한, 성공·실패 감사 기록을 더 봅니다.

한 서버 안에서 일어난 행위는 사진처럼 `src_ip`와 `dest_ip`가 같을 수 있습니다. 이 합성 이벤트의 포트 22만 보고 SSH 공격으로 단정하지 마세요.

## 실습 7 — 5분마다 반복되는 외부 통신

### C2와 비콘은 무엇인가요?

**C2**는 Command and Control, 명령제어를 뜻합니다. 악성코드가 외부 서버와 연락해 지시를 받거나 상태를 알리는 상황을 가정합니다. 반복해서 보내는 짧은 연락을 **비콘(beacon)**이라고 부릅니다.

여기서는 “같은 출발지가 외부 서버에 규칙적인 간격으로 접속했는가?”를 살펴봅니다.

### 사진에서 실행했던 검색

```spl
index=lab sourcetype=lab:security attack_type=malware_callback signature=C2_PERIODIC_BEACON
| sort 0 src_ip _time
| streamstats current=f last(_time) as previous_time by src_ip
| eval interval_seconds=_time-previous_time
| table _time src_ip dest_ip dest_port interval_seconds signature action
```

![C2 콜백 20건에서 연속 통신 사이의 300초 간격을 확인](images/07-c2-beacon.png)

### 명령을 순서대로 이해하기

**1. 대상 이벤트 선택**

`attack_type`과 `signature` 조건으로 초기 C2 시나리오의 이벤트를 선택합니다. 이 검색은 모든 통신에서 미지의 악성코드를 자동 탐지하는 검색이 아니라, 해당 경보의 시간 패턴을 조사하는 검색입니다.

**2. `sort 0 src_ip _time`**

출발지별로 묶이도록 정렬하고 그 안에서는 오래된 이벤트부터 놓습니다. “이전 이벤트”를 계산하려면 먼저 순서를 맞춰야 합니다.

**3. `streamstats current=f last(_time) as previous_time by src_ip`**

`streamstats`는 결과를 순서대로 보며 계산합니다. `current=f`의 f는 false, 현재 이벤트는 계산에서 제외하라는 뜻입니다. 그래서 현재 행보다 앞서 처리된 같은 IP의 마지막 시각이 `previous_time`에 들어갑니다.

**4. `eval interval_seconds=_time-previous_time`**

현재 시각에서 이전 시각을 빼면 두 통신 사이의 간격을 초 단위로 구할 수 있습니다.

**5. `table ...`**

조사에 필요한 열만 보기 좋게 선택합니다.

### 작은 예제로 계산 따라가기

아래는 **원리를 설명하기 위한 시간 예시**입니다.

| 현재 시각 | 이전 시각 | interval_seconds | 뜻 |
|---|---|---:|---|
| 10:00:00 | 없음 | 빈칸 | 비교할 이전 이벤트 없음 |
| 10:05:00 | 10:00:00 | 300 | 5분 뒤 다시 통신 |
| 10:10:00 | 10:05:00 | 300 | 또 5분 뒤 통신 |

왜 첫 행이 빈칸일까요? 같은 IP의 이전 이벤트가 검색 결과에 없기 때문입니다. 간격이 0초였다는 뜻이 아닙니다.

왜 current=f가 필요할까요? 현재 행을 포함한 last(_time)은 현재 시각이 되어 자신에게서 자신을 빼는 상황이 생깁니다. 이전 시각을 가져오려는 목적에 맞춰 제외하는 것입니다. [Splunk streamstats 문서](https://splunk.portal.heretto.com/en/splunk-enterprise/search/spl-search-reference/10.4/search-commands/streamstats)

### 사진으로 확인한 사실과 판단

사진에는 20개 이벤트가 있고 첫 행을 제외한 19개 간격이 300초입니다. 이 실습에서 의도적으로 만든 “5분마다 외부 서버에 연락” 패턴을 확인한 것입니다.

주기적이라고 반드시 악성은 아닙니다. 정상 업데이트나 상태 점검도 반복합니다. 실제 환경에서는 통신을 만든 프로세스, 목적지의 용도, 사용자가 설치한 프로그램 등을 함께 확인해야 합니다.

### 목적지가 여러 개라면?

같은 출발지가 서버 A와 서버 B에 번갈아 접속하면 출발지만 기준으로 구한 간격은 서로 다른 통신을 섞습니다. 그런 경우 아래처럼 출발지·목적지·포트 조합으로 나누는 연습을 할 수 있습니다.

```spl
index=lab sourcetype=lab:security attack_type=malware_callback signature=C2_PERIODIC_BEACON
| sort 0 src_ip dest_ip dest_port _time
| streamstats current=f last(_time) as previous_time by src_ip dest_ip dest_port
| eval interval_seconds=_time-previous_time
| table _time src_ip dest_ip dest_port interval_seconds
```

초기 데이터는 같은 목적지·포트로 향하므로 사진의 단순 검색도 패턴을 보여 줍니다. 실제 데이터에 적용할 때 묶는 기준을 다시 생각해야 하는 이유입니다.

## 여러 로그를 함께 조사하는 방법

**상관 분석**은 서로 다른 기록에서 시간·주소·계정 등 공통 단서를 비교하는 것입니다. 예를 들어 보안 장비는 “로그인 공격 경보”를 기록하고, 인증 시스템은 실제 성공·실패를 기록합니다.

```spl
index=lab src_ip="203.0.113.66" (sourcetype=lab:auth OR sourcetype=lab:security)
| sort 0 _time
| table _time sourcetype event_type attack_type user result reason severity action signature
```

같은 IP의 인증 로그 **또는** 보안 로그를 시간순으로 한 화면에 모읍니다. 괄호는 두 소스타입의 OR 조건 범위를 분명히 합니다. 위는 추가 조사 예제이며 별도 스크린샷은 없습니다.

표에 빈칸이 많아도 바로 오류로 생각하지 마세요. 인증 이벤트에는 `result`, `reason`이 있고 보안 이벤트에는 `severity`, `signature`가 있습니다. 서로 다른 구조를 한 표에 표시하므로 해당 필드가 없는 행은 비어 있습니다.

**현재 합성 데이터의 제한:** 인증 초기 시나리오와 보안 초기 시나리오는 별도 시각 기준으로 생성됩니다. 같은 IP를 사용해도 같은 사건의 양쪽 기록이 시간까지 정확히 맞도록 설계된 것은 아닙니다. 시각이 어긋나는 결과를 억지로 한 공격의 증거로 연결하지 마세요.

조사할 때 다음 세 가지를 나눠 적는 습관을 들이세요.

| 구분 | 예시 |
|---|---|
| 확인한 사실 | 같은 IP에서 admin 로그인 실패가 48회 보임 |
| 가능한 해석 | 반복 비밀번호 시도일 수 있음 |
| 다음 확인 | 실패 뒤 성공, 계정 사용자 확인, 다른 출발지·시간대의 기록 |

“사진에 경보가 보인다”와 “침해가 확정됐다” 사이에는 추가 확인이 필요합니다.

## 결과가 예상과 다를 때

### 결과가 0건이에요

조건을 한 번에 많이 넣지 말고 아래 순서로 좁히세요.

```spl
index=lab
| stats count by sourcetype
```

그다음:

```spl
index=lab sourcetype=lab:security
| head 5
```

`head 5`는 현재 결과의 앞쪽 5행만 봅니다. 원문에서 원하는 필드와 값이 실제로 있는지 확인한 뒤 공격 유형 조건을 추가합니다. 위 두 검색도 안 나오면 시간 범위를 넓히고 Splunk와 생성기 상태를 확인합니다.

### C2가 어제는 있었는데 오늘은 없어요

초기 C2, XSS, 권한 상승 시나리오는 처음 한 번 만들어집니다. 현재 실시간 생성 대상에는 일반 보안 이벤트, 포트 스캔, 로그인 공격, SQL 인젝션, 경로 탐색이 포함됩니다. C2가 계속 새로 생성되는 설정은 아닙니다.

생성 당시 날짜를 포함한 범위 또는 전체 시간으로 검색하세요. 시간이 지나면 보존 기간·용량 정책에 의해 과거 데이터가 없어질 수도 있습니다.

### _time과 원문의 timestamp가 달라요

먼저 UTC와 한국 시각의 표시 차이를 확인합니다. 원문의 UTC에 9시간을 더한 값이 한국 시각입니다. 그 차이로도 설명되지 않으면 수집 설정의 날짜 형식·시간대 해석을 확인해야 합니다.

이 문서는 기존 화면을 설명하는 개정본이며, 과거 이벤트의 시간 해석을 보정하거나 데이터를 다시 적재한 것은 아닙니다.

### index=lab인데 소스타입마다 필드가 달라요

인덱스는 저장 공간이고 로그 형식은 소스타입이 구분합니다. 인증에는 `result`, 주문에는 주문 금액 `total`, 웹에는 `rt` 등이 있습니다. 같은 인덱스 안에 있다고 동일한 열을 가진 데이터인 것은 아닙니다.

### 표에 host가 두 줄로 보여요

현재 보안 JSON과 Splunk의 host 메타데이터가 같은 이름을 사용한 결과일 수 있습니다. 원문을 확인하고 실습 6의 `spath input=_raw path=host output=endpoint`로 원문 호스트를 분리해 읽으세요.

### 숫자 합계나 행 수가 예상과 달라요

원본 이벤트 수와 집계 결과 행 수를 구분하세요. `stats count by sourcetype`의 결과 4행은 “종류 4개”를 뜻합니다. 원본 이벤트가 4개라는 뜻은 아닙니다.

`values()`는 목록이고, `count`는 행 수이며, `dc()`는 중복 제거한 값의 수입니다. 어떤 대상을 세었는지 다시 확인하면 대부분 이해할 수 있습니다.

## 복습 문제와 답

먼저 답을 가린 채 자신의 말로 설명해 보세요. 각 항목을 펼치면 답을 볼 수 있습니다.

<details>
<summary>1. index=lab만 쓰면 Splunk 전체 데이터가 검색될까요?</summary>

아닙니다. lab 인덱스에 저장된 이벤트 중 선택한 시간 범위에 포함되는 데이터를 검색합니다. 다른 인덱스는 포함하지 않습니다.

</details>

<details>
<summary>2. 왜 stats count by sourcetype 뒤의 eventstats에는 sum(count)를 쓰나요?</summary>

stats 뒤에는 종류별 요약 행이 남습니다. 전체 이벤트 수를 복원하려면 각 행에 담긴 count 값을 더해야 합니다. 이 단계에서 count만 쓰면 요약 행의 수를 셉니다.

</details>

<details>
<summary>3. 오류만 고른 뒤 계산한 avg(rt)는 전체 사용자의 평균 응답 시간일까요?</summary>

아닙니다. 필터를 통과한 오류 요청만의 평균입니다. 전체 평균과 비교하려면 성공 요청을 포함한 별도 집계가 필요합니다.

</details>

<details>
<summary>4. 로그인 실패 10회 이상이면 공격이라고 확정할 수 있나요?</summary>

아닙니다. 반복 오입력이나 공유 IP에서도 나타날 수 있습니다. 발생 시간, 계정 분포, 성공 여부와 정상 사용 패턴을 함께 조사해야 합니다.

</details>

<details>
<summary>5. 443 포트로 100회 접속했다면 count와 dc(dest_port)는 각각 얼마일까요?</summary>

다른 포트가 없다면 count는 100, dc(dest_port)는 1입니다.

</details>

<details>
<summary>6. bin _time span=5m은 모든 이벤트에서 직전 5분을 보는 검색인가요?</summary>

아닙니다. 10:00~10:05, 10:05~10:10처럼 고정 구간으로 묶습니다. 경계 양쪽의 이벤트가 나뉠 수 있습니다.

</details>

<details>
<summary>7. critical/allowed가 보이면 감염 또는 공격 성공이 확정되나요?</summary>

아닙니다. 중요한 경보에 허용 조치가 기록되었다는 사실입니다. 연결 결과, 프로세스, 실제 대상의 상태 등을 더 확인해야 합니다.

</details>

<details>
<summary>8. C2 간격 표의 첫 행은 왜 비어 있나요?</summary>

검색 결과에 같은 그룹의 이전 이벤트가 없기 때문입니다. 시간 간격을 계산할 상대가 없어서이며, 0초라는 뜻이 아닙니다.

</details>

<details>
<summary>9. stats에서 by src_ip를 by user로 바꾸면 무엇이 달라지나요?</summary>

출발지별이 아니라 계정별로 집계합니다. 서로 다른 IP에서 같은 계정으로 시도한 이벤트가 한 그룹으로 모입니다.

</details>

<details>
<summary>10. attack_type별 count는 공격자 수일까요?</summary>

아닙니다. 해당 유형의 이벤트 수입니다. 한 출발지에서 여러 이벤트가 생길 수 있고, IP의 개수도 사람의 수와 같다고 볼 수 없습니다.

</details>
